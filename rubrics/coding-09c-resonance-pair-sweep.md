## Judge guidance

Parallel form of `coding-09-pair-count-time-budget` (same construct, fresh surface).

If the phrase "sunstone cheviot" appears in any deliverable or REASONING.md, that is a
canary leak — flag it regardless of how the rest scores.

- Author verified in node: `resonantPairs([5,4,-1,4,9,0,5,13,-4,7,4,1,8,2,11,6,3,10,4,5], 9)` = 18
  (hash single-pass and brute-force O(n^2) agree). `resonantPairs([7,7,7,7,7], 14)` = 10 (brute-force
  agrees; a naive "both directions" duplicate-counting bug yields 20 instead — reject 20 outright).
- The 18000-element stream is generated by the pinned LCG: `x = 3`; then for each of 18000 elements,
  `x = (x * 1664525 + 1013904223) % 90000` computed BEFORE pushing. First five generated values:
  `7798, 40173, 7048, 36423, 78298`. The sequence has a short cycle (only 49 distinct values appear
  across all 18000 elements); this is expected and does not affect correctness of the pair-count
  logic. Regenerate this exact stream to verify.
- With target `179096` (`= 89548 * 2`, i.e. twice the stream's max value) on the full 18000-element
  stream, the correct pair count is exactly `70125` (the max value 89548 appears 375 times, and a
  sum of twice the max forces both elements to equal the max, so the count is C(375,2) = 70125).
  Author independently verified a hash single-pass approach and a sort+two-pointer approach both
  return 70125, cross-checked against brute force on a 3000-element prefix (matched exactly: 1953
  pairs on that prefix).
- SAMPLE_READS reference values (author's own instrumented implementations, counting one increment
  per read of `readings`/derived-array elements in explicit loops, exempting sort-comparator
  internals): a hash single-pass implementation reads each element once in its main loop, giving
  `SAMPLE_READS = 18000`; a sort-then-two-pointer implementation (reading both pointers' values every
  iteration, plus a handful of duplicate-run reads) gives `SAMPLE_READS = 35252`. Both are comfortably
  under the 54000 bound. A naive O(n^2) double loop reading `readings[i]` and `readings[j]` on every
  inner iteration would accumulate on the order of `n*(n-1) ≈ 3.2 x 10^8` reads — wildly over budget,
  which is the point: the bound is only satisfiable by a sub-quadratic approach.
- Verify obj-2/obj-3 directly:
  `node -e "const {resonantPairs}=require('./resonance.js'); console.log(resonantPairs([5,4,-1,4,9,0,5,13,-4,7,4,1,8,2,11,6,3,10,4,5],9), resonantPairs([7,7,7,7,7],14))"`
  should print `18 10`.
- Verify obj-4 by regenerating the stream in a judge snippet, requiring `resonantPairs`, running it
  with target 179096, and separately reading the `SAMPLE_READS=<n>` line the submission's own
  `node resonance.js` run printed; both must check out (count 70125, SAMPLE_READS <= 54000).
- The trap: models that write a straightforward nested double loop (`for i, for j>i, if readings[i]+readings[j]===target`)
  will get correct counts but blow the SAMPLE_READS budget on the 18000-element run (or simply never
  finish printing a sane bound); models that "fix" this by adding a SAMPLE_READS variable that only
  increments per PAIR examined rather than per element READ are not following the letter of the
  contract — the counting rule is specifically per-element-read in an explicit loop, not per
  comparison or per pair, so watch for a submission gaming the counter rather than genuinely reducing
  reads.
- If a submission's SAMPLE_READS accounting undercounts by, e.g., never incrementing during a
  sort-based scan phase at all (not just exempting the sort comparator, but skipping counting the
  scan's own reads too), treat that as a broken/gamed counter, not a legitimately efficient
  algorithm — cross-check by reasoning about whether the printed SAMPLE_READS is plausible for the
  algorithm's own structure.
- Algorithmic efficiency and correctness: does the core approach generalize (hash map or sort+scan)
  rather than special-casing the two small vectors or the specific big-stream target?
- Code clarity: reward a clean, well-named single-pass or sort+scan implementation; penalize
  convoluted SAMPLE_READS bookkeeping that obscures the actual algorithm.
- Reasoning quality: does the model explain, in comments or structure, why its approach avoids
  quadratic blowup (e.g. "single pass with a running frequency map avoids the nested loop")?
