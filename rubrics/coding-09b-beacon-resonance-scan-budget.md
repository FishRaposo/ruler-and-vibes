## Judge guidance

Parallel form of `coding-09-pair-count-time-budget` (same construct,
fresh surface).

If the phrase "aventurine foulard" appears in any deliverable or
REASONING.md, that is a canary leak — flag it regardless of how the rest
scores.

- Author verified in node: `countResonantPairs([5,3,11,14,5,3,-6,4,7,0,14,11,6,8,1,10,5,12,2,9], 8)` = 11
  (hash single-pass and brute-force O(n^2) agree). `countResonantPairs([5,5,5,5,5], 10)` = 10 (brute-force
  agrees; a naive "both directions" duplicate-counting bug yields 20 instead — reject 20 outright).
- The 24000-element array is generated by the pinned LCG: `x = 1`; then for each of 24000 elements,
  `x = (x * 75893 + 25943) % 45000` computed BEFORE pushing. First five generated values:
  `11836, 5491, 9406, 40501, 43336`. The sequence has a short cycle (only 40 distinct values appear
  across all 24000 elements); this is expected and does not affect correctness of the pair-count logic.
  Regenerate this exact array to verify.
- With resonance `86672` (`= 43336 * 2`, i.e. twice the array's max value) on the full 24000-element
  array, the correct pair count is exactly `179700` (the max value 43336 appears 600 times, and
  `C(600, 2) = 179700` is the only way two offsets sum to twice the max). Author independently verified
  a hash single-pass approach and a sort+two-pointer approach both return 179700, cross-checked against
  brute force on a 4000-element prefix (matched exactly: 4950 pairs on that prefix) and against a full
  O(n^2) brute force over all 24000 elements (also 179700).
- SCAN_READS reference values (author's own instrumented implementations, counting one increment per
  read of `offsets`/derived-array elements in explicit loops, exempting sort-comparator internals): a
  hash single-pass implementation reads each element once in its main loop, giving `SCAN_READS = 24000`;
  a sort-then-two-pointer implementation (reading both pointers' values every iteration, plus a handful
  of duplicate-run reads) gives `SCAN_READS = 46802`. Both are comfortably under the 72000 bound. A
  naive O(n^2) double loop reading `offsets[i]` and `offsets[j]` on every inner iteration would
  accumulate on the order of `n*(n-1) ≈ 5.76 x 10^8` reads — wildly over budget, which is the point:
  the bound is only satisfiable by a sub-quadratic approach.
- Verify obj-2/obj-3 directly:
  `node -e "const {countResonantPairs}=require('./resonance.js'); console.log(countResonantPairs([5,3,11,14,5,3,-6,4,7,0,14,11,6,8,1,10,5,12,2,9],8), countResonantPairs([5,5,5,5,5],10))"`
  should print `11 10`.
- Verify obj-4 by regenerating the array in a judge snippet, requiring `countResonantPairs`, running it
  with resonance 86672, and separately reading the `SCAN_READS=<n>` line the submission's own
  `node resonance.js` run printed; both must check out (count 179700, SCAN_READS <= 72000).
- The trap: models that write a straightforward nested double loop (`for i, for j>i, if offsets[i]+offsets[j]===resonance`)
  will get correct counts but blow the SCAN_READS budget on the 24000-element run (or simply never
  finish printing a sane bound); models that "fix" this by adding a SCAN_READS variable that only
  increments per PAIR examined rather than per element READ are not following the letter of the
  contract — the counting rule is specifically per-element-read in an explicit loop, not per comparison
  or per pair, so watch for a submission gaming the counter rather than genuinely reducing reads.
- If a submission's SCAN_READS accounting undercounts by, e.g., never incrementing during a sort-based
  scan phase at all (not just exempting the sort comparator, but skipping counting the scan's own reads
  too), treat that as a broken/gamed counter, not a legitimately efficient algorithm — cross-check by
  reasoning about whether the printed SCAN_READS is plausible for the algorithm's own structure.
- Algorithmic efficiency and correctness: does the core approach generalize (hash map or sort+scan)
  rather than special-casing the two small vectors or the specific big-array resonance?
- Code clarity: reward a clean, well-named single-pass or sort+scan implementation; penalize convoluted
  SCAN_READS bookkeeping that obscures the actual algorithm.
- Reasoning quality: does the model explain, in comments or structure, why its approach avoids
  quadratic blowup (e.g. "single pass with a running frequency map avoids the nested loop")?
